# Desi Bazaar — API Specification v1.0 (for review, 2026-10-08)

_Basis: SRS v1.5 FROZEN, design doc §9 (transaction appendix)._
_Conventions: REST + JSON. Auth: OTP session tokens (NFR-S1). All order mutations go through the command endpoint — no direct dimension writes. Authorisation is enforced server-side (NFR-S3); client-supplied IDs are never trusted for cross-account access._

## 1. Command endpoint (order mutations)

`POST /v1/commands`

```json
{
  "operation_id": "uuid-v4-client-generated",
  "order_id": "uuid",
  "operation": "report_payment",
  "expected_order_version": 4,
  "payload": {},
  "evidence_references": []
}
```

- `operation` ∈ `report_payment | confirm_payment | mark_dispatched | confirm_receipt | request_cancellation | report_refund | acknowledge_refund | contest_refund | open_dispute | decide_dispute | request_return | authorise_return | ship_return | confirm_return_receipt | ...` (one per §11 event; full list in implementation)
- **Operation identity:** `operation_id` is generated by the client, one per logical operation. The server binds it to `(authenticated principal, order_id, operation, fingerprint=H(order_id, operation, canonical_payload))`:
  - same ID + same fingerprint → recorded result returned, nothing re-executes;
  - same ID + different fingerprint → `409 OPERATION_CONFLICT`, no mutation;
  - another principal replaying the ID → `403`.
- Actor identity comes from the authenticated session — never from request fields. Object-level authorisation runs before processing or replay.
- `expected_order_version` mismatch → `409 VERSION_CONFLICT`, no writes (default contract; no silent re-evaluation).
- Permitted actor / required evidence per §11 row; violations → `403` / `422`, nothing committed.
- Success → `200` with new dimension values + new `order_version`. Notifications are committed to the outbox in the same transaction and delivered after.

`GET /v1/orders/{id}` — returns the five dimensions, `order_version`, snapshot, refund-action ledger (derived totals), linked return/dispute/review. Only buyer, seller, or admin.

## 2. Sellers (FR-S)

- `POST /v1/sellers/applications` — submit (ID document upload → encrypted object ref, never a URL)
- `GET /v1/sellers/applications/mine` — status
- `PATCH /v1/sellers/me/recipient` — change Swish recipient → triggers re-auth + notification + hold (FR-S6)
- Admin: `GET /v1/admin/seller-queue`, `POST /v1/admin/sellers/{id}/decision` (versioned checklist; reviewer identity + timestamp recorded)

## 3. Listings (FR-L, FR-B)

- `POST /v1/listings` (seller, approved only), `PATCH /v1/listings/{id}`, `GET /v1/listings?q=&category=&size=&max_price=&condition=` (FR-B2)
- `GET /v1/listings/{id}` — full detail incl. seller badge scope/date, fulfilment options, total price
- `POST /v1/listings/{id}/reserve` — atomic reservation → creates order + immutable snapshot (FR-L2/L3). Fails atomically if no unit left.

## 4. Chat (FR-C)

- `GET /v1/orders/{id}/chat`, `POST /v1/orders/{id}/chat/messages` — order-bound threads only
- Contact fields are redacted until order confirmation; afterwards purpose-limited (FR-C2)
- `POST /v1/users/{id}/block`

## 5. Disputes & returns (FR-D)

- Via `/v1/commands` (`open_dispute`, `decide_dispute`, `request_return`, …)
- `GET /v1/disputes/{id}` — evidence, proposed outcome, remedy outcome (separate fields, FR-D3)
- Admin: `GET /v1/admin/dispute-queue` (SLA timers), `GET /v1/admin/report-queue`

## 6. Reviews (FR-R)

- `POST /v1/orders/{id}/review` — one per order; eligibility checked server-side (FR-R1: evidenced fulfilment or qualifying failed transaction)
- `GET /v1/sellers/{id}/reviews`, `GET /v1/sellers/{id}/profile` (badge + scope, fulfilment history with unconfirmed shown separately — NFR-BR3)

## 7. Deletion & privacy (FR-DEL, NFR-PR)

- `POST /v1/users/me/deletion` — starts the deletion flow; `GET /v1/users/me/deletion/status` (what completed, exceptions)
- Public (no auth): `GET /v1/public/deletion` — web entry point (FR-DEL1)

## 8. Admin (FR-A)

- `GET /v1/admin/queues` — sellers, disputes, reports, each with owner + SLA timer
- `POST /v1/admin/service/pause`, `POST /v1/admin/service/resume` (FR-A3)
- All admin endpoints require MFA; all actions audit-logged (FR-A2)

## 9. Errors

`400` validation · `401` auth · `403` authorisation (incl. object-level) · `404` · `409 VERSION_CONFLICT` · `422` guard/evidence failure · `429` rate-limited. Error bodies carry a stable `code` (e.g. `GUARD_DISPATCH_BEFORE_PAYMENT`) — never a stack trace.
